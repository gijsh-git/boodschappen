## Receipts

"Bon scannen" in the `aankopen` view works like the photo flow, but the file input is `multiple`: `startStapel()` puts every chosen file in the module-level `bonStapel` (max `BON_MAX`), and `leesVolgende()` reads them in the background, `BON_TEGELIJK` at a time. `leesBon(bon)` shrinks the image with `verkleinFoto()` (a pdf, e.g. the digital receipt from the AH app, is sent as is by `leesBonBestand()`) and calls the Edge Function `bon-uploaden`, which returns `{ bon: { supermarkt, datum, totaal, regels: [{ bon_naam, naam, aantal, prijs, korting }] } }` or `{ fout }`. `naam` is the readable product name the model makes from the receipt text; the rules live in `INSTRUCTIES` in the function. Nothing is written and the photo is not stored anywhere. One file opens the `bon` view directly; several open the `stapel` view ("Bonnen controleren"), an overview with per receipt its state (`status`: `wacht`, `lezen`, `klaar`, `fout`, `opgeslagen`) and what `bonTwijfels()` finds odd about it (store, date or total missing, lines not adding up to the total, a line without a price, duplicate receipt in the database or in the stack, lines that match a purchase of that day, lines that only resemble an item on the list). Tapping a read receipt opens it in the `bon` view (`bonHuidig`; the header inputs write straight into that stack entry, so edits survive going back). "Alles zonder bijzonderheden opslaan" saves the receipts without doubts one by one and re-runs `controleerBon()` right before each, so a receipt that became a duplicate through the one just saved stays behind for review. The stack lives in memory only: `leegStapel()` drops it on list switch and logout, and `bonVraag` makes late answers harmless. While it holds unsaved receipts the `aankopen` view shows "Bonnen controleren (n)"; `aankopenOpen` stays set in both views, so `route()` leaves them alone. The `bon` view lets you correct store, date, total and lines; `controleerBon(bon)` calls `receipt_exists` (same store, date and total already saved: warning plus a confirm on save) and `match_receipt_lines`, which finds for each line the most similar purchase of the same day with pg_trgm, with its own threshold (`0.5`), and `match_receipt_items` (see below). Saving (`bewaarBon()`) goes through `save_receipt(p_list, p_store, p_date, p_total, p_lines)`, which refuses archived lists (it works on lists that do not count for the profile too). A product counts once per day per name and article id: a line linked to an existing purchase fills in `receipt_id`, `receipt_name`, `price`, `discount` and `article_id` on that row instead of adding one; a line linked to a purchase that already has receipt data, or with exactly the same name as a purchase of that day, is skipped, unless both have an `article_id` and they differ (two sizes with the same receipt text are two purchases). `purchases.article_id` (text) is the article number on the receipt, in the system of the supermarket on that receipt (`receipts.store`); for AH that is the `hqId`, not the webshop id. Only the AH import sends it: a scanned photo has no article number, so the app never does. New rows get the receipt date at 12:00 Amsterdam time as `bought_at`. A receipt also takes items off the list: `match_receipt_items(p_list, p_date, p_names)` (`security definer`, because a member may not read the alias of a new receipt name yet) finds per line the best item that was added on or before the receipt date (Amsterdam days) and returns `zeker` when it is the same name or the same type through `name_type()`, otherwise it only passed the pg_trgm threshold (`0.5`). The `bon` view shows it in the same row as the purchase link (`toonKoppel()`; a line linked to a purchase of that day gets no item, `lijstItem()`): the same product is ticked by default, a look-alike only when the user ticks it (`regel.itemAan`, `vanLijst()`), and an undecided look-alike is a doubt in `bonTwijfels()`, so the stack never removes it on its own. `save_receipt` gets the `item_id` per line, checks the date again, deletes the item and inserts the purchase like `buy_item` does (item name, `item_id`, `added_by`, `item_created_at`) with the receipt data, in the same transaction; it counts them as `van_lijst`. Deleting the receipt later keeps that purchase and does not put the item back. `receipts` (`store`, `receipt_date`, `total`) only exists to recognise duplicate receipts. One photo per receipt. "Gescande bonnen" in the `aankopen` view opens the `bonnen` view (`toonBonnen()`; `aankopenOpen` stays set): the receipts of the list, each expandable to the purchases that carry its `receipt_id`, and a × that calls `delete_receipt(p_receipt)`. That RPC deletes the purchases that only came from the receipt (`item_id` is null), clears the receipt columns (including `article_id`) on purchases that were linked, and removes the receipt. `receipts` is not in the realtime publication; the view refetches when opened.

## Historic AH receipts

Two scripts outside the app, both run by hand. `scripts/ah-bonnen` (Go, uses the `appie-go` library and the login tokens that the `ah-mcp` MCP server stores) only reads from the AH account and writes all receipts with their lines to `data/ah-bonnen.json`; `data/` is not in git. `scripts/ah-importeren.py` (Python, standard library only) logs in to Supabase with the app's email and password and stores them through the same RPCs as "Bon scannen" (`receipt_exists`, `match_receipt_lines`, `save_receipt`), so re-running adds nothing twice. Without `--echt` it is a dry run. AH only gives the abbreviated receipt text; `data/ah-namen.json` maps each text to a readable name, and lines that get the same name and the same `product_id` are merged. Discounts come per receipt and are matched to lines by name (`past()`), the ones that fit no line are dropped. The product id on a receipt is not a webshop id but AH's `hqId`, which every bonus article carries next to its webshop id; the import sends it as `article_id`. `scripts/ah-artikel-aanvullen.py` (dry run without `--echt`, reuses `ah-importeren.py`) fills `article_id` on AH purchases imported before that: it finds the receipt in `data/ah-bonnen.json` by date and total and the line by `receipt_name`, and writes through the `security definer` RPC `fill_article_ids(p_rows)`, which only touches purchases with a receipt in your lists and never overwrites an id.

## AH bonus exploration

`scripts/ah-bonus` (Go, `appie-go` with an anonymous token, no account) writes the current bonus week to `data/ah-bonus.json`: per offer the discount text and labels, validity, and its articles with `webshop_id`, `hq_id`, title, brand, size and category; a group whose articles could not be fetched after three tries gets `mislukt`. `scripts/ah-bonus-vergelijken.py` (Python, standard library, reuses `ah-importeren.py`) lays that next to `data/ah-bonnen.json` and counts which offers hit something we buy, by id and by name. Both only read; storing the week in the database is `scripts/ah-bonus-opslaan.py` (see "Offers"). The findings are in `docs/verkenning-ah-bonus.md`.
