# Producttypes en termen matchen

> Deel van de systeembeschrijving; de index staat in `CLAUDE.md`. Een verwijzing als (see "Offers") gaat naar een kopje in dit bestand of in een ander bestand in `docs/systeem/`; de index zegt welk. Werk dit bestand bij in dezelfde commit als de wijziging die het gedrag verandert.

## Product types

A fixed list of product types with automatic classification (roadmap step 5 part 4); the profile, Voor jou, the Bonus label and the favourites run on types, and nothing waits for approval. There is no merging of names. The old catalogue is gone; do not bring it back: the tables `products`, `product_aliases`, `product_merges`, `article_links`, `article_link_rejections` and `article_names`, their RPCs and the trigger `ensure_product()` were dropped in the migration `oude_catalogus_weg` (their last contents are in `data/backup/20261009-oude-catalogus.json`, not in git). `product_types` (`name`, generated unique `key` through `match_key`, generated `stem`, `main_group`: the supermarket's main category or "Geen boodschappen", `scope`, `excludes`, `counts_in_profile`) has no policies or grants. A type is the level where a buyer switches for an offer (`docs/productregels.md`). **The database is the source of the type list.** Types are created with `create_product_type(p_name, p_main_group, p_scope, p_excludes, p_counts, p_suggestion)` (terms and articles without a type whose `suggested_type` equals `p_suggestion` get the new type at once, the other untyped articles are judged again), changed with `update_product_type(p_type, …)` (after a rename the old name keeps working as a name of the type) and merged with `merge_product_types(p_source, p_target)` (by name: moves the articles, names and items of the source, deletes it and keeps its name as a name of the target); all admin only, from the screen "Koppelingen". `docs/producttypes-export.csv` is a printout, never an input: `scripts/producttypes-exporteren.py` rewrites it from the database through the Edge Function `producttypes-exporteren` (no JWT verification, same header and secret as `aanbiedingen-opslaan`; reads `product_types_export()`, service role only) with `AANBIEDINGEN_SLEUTEL` from the environment or `.env`, without a login, and `.githooks/pre-commit` runs it on every commit and adds the file (enable once per clone with `git config core.hooksPath .githooks`; when reading fails the commit continues with a warning). The file holds only the types, not the names that belong to them (what people typed or bought; the repo is public) and no article counts (they change every bonus week). Never edit it by hand and never load types from a file. `save_term_types()` and `set_article_types()` (admin only) are what the screen uses to correct a name or an article (source `manual`). `article_types` (primary key `supermarket` + `article_id`, `type_id` or null for "no type" with `suggested_type`, `confidence`, `reason`, `source` `ai`/`receipt`/`catalog`/`manual`, `judged_at`, `reviewed_at`; no policies or grants) holds the type of an article. The Edge Function `artikelen-classificeren` (no JWT verification, same header and secret as `aanbiedingen-opslaan`, model in `MODEL`) reads `article_type_work(p_limit)` (articles without a row, or without a type while types were added since `judged_at`; plus the whole type list in a fixed order for prompt caching), asks the Claude API per `PORTIE` articles (`TEGELIJK` portions at once) for a type name from the list or "geen type", and writes through `save_article_types(p_rows, p_judged_at)`, which only replaces unreviewed `ai` rows; both RPCs are service role only. `scripts/ah-bonus-opslaan.py --echt` calls it after saving until nothing is left (`--types` does only that), so new articles get a type in the same run as the weekly fetch. `term_synonyms` is the one table name → type (`type_id`, null meaning judged without a type, then with `suggested_type` for the type the AI misses; `brand_key`, `confidence`, `reason`, `reviewed_at`, generated `stem`; `source` is `manual`, `ai` or `catalog`, in that order of precedence). `save_term_types_internal(p_rows, p_source)` writes it without a role check (for the Edge Function and `add_offer_item`); a term that is itself a type name never gets a row, because the type name wins. `set_article_types(p_rows, p_source)` sets the type of an article and marks it reviewed. `purchase_types()` (service role only) derives the type of a purchase, never stored: the article on the receipt first, then the name. `docs/producttypes-controle.sql` holds check queries (what has a type, what does not, what the AI could not place). The screen "Koppelingen" (the `producten` view, `toonKoppelingen()`, opened from `profiel` with "Koppelingen beheren", admin only, `profielOpen` stays set) is where the admin checks and corrects what the AI linked; nothing waits for approval. Three collapsible blocks show what needs attention: "Termen" (AI-judged terms, newest first), "Artikelen om na te kijken" (per type, with "Alles klopt") and "Geen type" (grouped on the type the AI misses, with "Type aanmaken" and "Geen type nodig"); below them the searchable list of all types, each opening to a form (name, main group, scope, the switch "Telt mee in aankoopprofiel"), "Samenvoegen met een ander type" and its names and articles. Every row has "Klopt", "Ander type" (one search-as-you-type picker, `kpKiezer()`, reused everywhere) or "Geen type". State and rules are in `logica.js` (`Logica.laadKoppelingen()`, `artikelGroepen()`, `ontbrekend()`, `zoekTypes()`, `klopt()`, `zetTermType()`, `zetArtikelType()`, `maakType()`, `wijzigType()`, `voegTypesSamen()`; every action refetches the overview); `app.js` only renders (`renderKoppelingen()`, the `kp…` functions). `type_link_overview()` returns the AI-judged terms not yet reviewed, the articles judged with confidence medium or low not yet reviewed, the articles without a type, and all types with their counts; `type_details(p_type)` the names and articles of one type; `mark_links_reviewed(p_terms, p_articles)` only sets `reviewed_at`. `reset_untyped_articles()` also kicks `artikelen-classificeren` through `pg_net` (address in Vault under `artikelen_classificeren_url`).

## Matching list terms

For the Bonus label only. `term_match(p_name)` says what a typed term stands for, as one row `(step, type_id, brand_key)` or no row when it matches nothing; the first layer with a hit wins: the name of a type (step 1; curated, always first), a brand (`articles.brand_key`, step 3: whoever types exactly a brand means everything of that brand, even when the name hangs on one type for the profile), a name in `term_synonyms` (step 2; with `brand_key` it means that brand within the type, and a row without a type means judged and belonging nowhere: a row, no articles), the same after Dutch stemming (`stem` on `product_types` and `term_synonyms`, from `list_stem`), a brand plus a kind in either order ("nivea shampoo", "tandpasta oral b": one part is a brand, the other resolves through `name_type()`; step 3 with both), and tolerant (step 4: pg_trgm `similarity` against type names, names and brands, only the best, from `fuzzy_min_similarity_pct` in `settings` and from 5 characters). `term_articles(p_name)` (same signature as before: `supermarket` in upper case, `article_id`, `step`) turns that into articles: all articles of the type, all articles of the brand, or the brand's articles within the type (falling back to the whole type when there are none), over all articles ever seen. A term that names a variant gets only the articles of that variant within the type (see "Variant"). `name_type(p_name)` is the type of a name for receipts and items: type name, then `term_synonyms`, then the stems; no brand layer and not tolerant, so a purchase "fanta" is sinas while the label for "fanta" covers everything of Fanta. `match_key(text)` is `normalize_search` with everything but letters and digits removed ("proteine drank" equals "proteinedrank"). `offers_for_list` and `offer_details_for_list` have two routes: the item's name through `term_articles()`, and `items.offer_id`. A term that stands for nothing goes to `handle_unmatched_term(p_name)`, the single point for unmatched terms, called by the trigger `items_term` (`check_item_term()`, insert or update of `name`, not for items with an `offer_id`; a known term without articles is not unmatched; an error there only raises a warning, so it never blocks adding an item). It upserts `unmatched_terms` (`key`, `term`, `times`, `first_seen`, `last_seen`, `claimed_at`, `judged_at`; no user or list) and then kicks the Edge Function `term-classificeren` through `pg_net` (`kick_term_classifier()`, which reads the function's address and the key from Supabase Vault under the names `term_classificeren_url` and `aanbiedingen_sleutel`; without them it does nothing; the request leaves after the commit). The function (no JWT verification, same header and secret as `aanbiedingen-opslaan`, model in `MODEL`) claims the open terms with `term_work(p_limit)`, asks the Claude API per term for a type name from the list or "geen type" plus the brand when the term names one, and stores the outcome with `save_term_judgments(p_rows)` (both service role only): a name in `term_synonyms` with source `ai` and the date, no approval beforehand, `judged_at` on the term, and `type_id` on the items with that name. That update arrives through Realtime, and the item UPDATE handler in `subscribe()` calls `loadDeals()` when `type_id` or the name changed, so the label appears for every member within seconds. The claim keeps a photo with many unknown items from judging the same terms more than once; a failed call leaves the terms open and they are picked up again after 3 minutes or by the weekly run (`scripts/ah-bonus-opslaan.py` calls the function too). The trigger `purchases_term` (`check_purchase_term()`) sends a purchase name without a type along the same point (a new receipt name, or an item that only matched tolerantly); a bare brand name stays without a type. A term judged without a type is never judged again. The helper functions have `execute` revoked for the app roles. The decisions are in `docs/productregels.md`; `docs/producttypes-controle.sql` holds check queries.
