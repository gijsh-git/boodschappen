# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"BonusBuddy" (folder and repo are still called `boodschappen`) is a shared grocery-list PWA for a household (two partners sharing one list). It is a static site with no build step, no package manager, no tests and no linter: plain HTML/CSS/JS talking directly to Supabase from the browser. All UI text, code comments, SQL policy names and CSS variable names are in Dutch; keep new ones in Dutch.

## Running

There is nothing to build. Serve the directory over HTTP (the service worker and Supabase auth redirect do not work from `file://`):

```sh
python3 -m http.server 8000
```

Before the app does anything useful:

1. The database is defined by the migrations in `supabase/migrations/`. For a fresh project: `supabase link --project-ref <ref>` and `supabase db push`. The first migration is a baseline dumped from the live database.
2. Fill in `SUPABASE_URL` and `SUPABASE_ANON_KEY` in `config.js`. While the URL still contains the `JOUW-PROJECT` placeholder, `init()` in `app.js` stops at the login view with a "fill in config.js" message.
3. The origin you serve from must be an allowed redirect URL in Supabase Auth, since invite and password-reset mails link back to `location.origin + location.pathname`.
4. For "Foto toevoegen": deploy `supabase/functions/foto-naar-items/index.ts` as Edge Function `foto-naar-items` with "Verify JWT" off (dashboard editor, or `supabase functions deploy foto-naar-items --no-verify-jwt`) and set the secret `ANTHROPIC_API_KEY`. "Bon scannen" needs `supabase/functions/bon-uploaden/index.ts` deployed the same way as Edge Function `bon-uploaden`; it uses the same secret. The functions are not part of the GitHub Pages deploy: after changing one, deploy it again.

The app is hosted on GitHub Pages from `main` (https://gijsh-git.github.io/boodschappen/), so pushing to `main` deploys.

## Architecture

**Load order matters.** `index.html` loads three classic scripts in order: supabase-js v2 from the jsDelivr CDN (global `supabase`), `config.js` (sets `window.CONFIG`), then `app.js`. There are no modules or imports.

**Views.** `index.html` holds sixteen `<section id="view-…">` elements (`login`, `forgot`, `sent`, `password`, `naam`, `profiel`, `producten`, `voorjou`, `setup`, `nieuw`, `list`, `aankopen`, `foto`, `bon`, `bonnen`, `stapel`); `show()` toggles their `hidden` attribute. Flow: `init()` → session check → `route()` fetches the user's `profiles` row (none yet → `naam` view to enter a display name once; it can be changed later in `profiel`, opened from the tab bar: the header shows your initial, name and e-mail address with a pencil button to edit the name, below it the purchase profile (see "Purchase profile") and a menu "Account" with "Producten beheren" (admin only) and "Uitloggen") → `loadLijsten()` fetches all the user's `list_members` rows into the module-level arrays `lijsten` (active) and `archief` (archived) → either `setup` (no lists yet) or `openList()` on the last opened list (id remembered in `localStorage` under `bonusbuddy-lijst`, falling back to the first list).

**Multiple lists.** The `setup` view is the overview "Mijn lijsten": it lists your lists (tap to switch) and is reachable from the list view by tapping the list name in the header (`lijsten-knop`). Its plus button opens the `nieuw` view, which holds the forms to create a list or join by pasting an invitation link. Each row has a switch "Meetellen voor aankoopprofiel", stored in `lists.counts_for_profile` (default true) through the `set_list_profile` RPC. The setting belongs to the list, so it is shared by all members; `buy_item` reads it to decide whether a purchase is stored (see "Purchases").

**Archiving and deleting.** Archiving is the normal way to get rid of a list, because deleting takes its purchases and receipts along (`on delete cascade`), and those are the basis of the purchase profile. The creator sees "Lijst archiveren" per row and, right of it, a bin button that calls `delete_list` after a confirm that warns about this (`verwijderLijst()`). Archiving calls `archive_list(p_list, p_archived)` and sets `lists.archived_at`. Archived lists leave the overview and show up in the collapsible block "Gearchiveerd" below it (`archiefRij()`), where the creator can put them back with "Terugzetten". Nothing can be added to an archived list: the insert policy on `items`, `join_list` and `save_receipt` all refuse it. Purchases and receipts stay and keep counting for the profile. A member who has the list open when it is archived is sent back to the overview by `verlaatLijst()`, triggered by the realtime UPDATE on `lists` or, after standby, by `controleerArchief()` in `loadItems()`.

`route()` runs again on every auth event (e.g. when the app returns to the foreground), so screens that must stay put set a flag it checks first: `naamOpen`, `profielOpen`, `voorjouOpen`, `lijstenOpen`, `aankopenOpen`, `fotoOpen`, `bonOpen`.

**Tab bar and back.** `<nav id="tabbalk">` (Lijst, Voor jou, Profiel) is fixed at the bottom; `show()` only shows it on the views in `TABS` (`list`, `setup`, `voorjou`, `profiel`) and marks the current tab. "Lijst" (`naarLijst()`) opens the overview "Mijn lijsten"; only when you have exactly one list it goes straight to that list. Sub-screens (`aankopen`, `bonnen`, `stapel`, `producten`, `nieuw`) have a round back button top left and `data-terug="<id of that button>"` on the section: `maakTerugveegbaar()` lets you swipe the screen to the right, which clicks that button. `foto` and `bon` keep "Annuleren" at the bottom and cannot be swiped away, because leaving them discards work.

**Voor jou.** The household's regular products, without any new database code: `loadVoorJou()` calls `purchase_profile('3m', null)` and uses its top 10 (`voorjou`). `renderVoorJou()` leaves out what is already on the open list (same name, case-insensitive) or was dismissed with "Niet nu" (`nietNu`, in memory only), and puts the product that is furthest past its usual interval (`om_de`) in the large card; `zetOpLijst()` inserts it into `items` of the open list. Offers are not linked to these products yet (roadmap fase 4 and 6).

**Auth is invite-only with passwords.** Signups are disabled in the Supabase dashboard; the owner adds people there with "Invite user". Login is `signInWithPassword`. "Wachtwoord vergeten?" goes `login` → `forgot` (request the mail) → `sent` (confirmation, with resend). Invite and reset mails land back on the app with `type=invite` / `type=recovery` in the URL hash, which `app.js` reads before creating the Supabase client (the client clears the hash). That sets `mustSetPassword`, which makes `route()` show the `password` view instead of the list until `updateUser({ password })` succeeds. Supabase's English auth errors are mapped to Dutch in `nl()`.

**Styling.** `styles.css` uses CSS variables with a dark-mode override, except the `.auth` screens (login, password), which pin the light values so they always look like the design. Fonts come from Google Fonts.

**State and sync.** `app.js` keeps a module-level `items` array as the single source of truth for rendering; `render()` rebuilds the `<ul id="items">` from it. Three things mutate it and must stay consistent:

- Local actions apply optimistically (`koop()`, `remove()`) and call `loadItems()` to resync if the Supabase write fails.
- A Supabase Realtime `postgres_changes` channel per list, filtered on `list_id`, applies INSERT/UPDATE/DELETE from the other user. Inserts are de-duplicated by `id` because your own insert arrives both from the `.insert().select()` response and from the realtime event.
- The same channel also listens to `list_members` (see "Members" below).
- A `visibilitychange` handler refetches everything when the app returns to the foreground, since phones drop the realtime socket in standby.

**Swipe.** There is no checking off any more: an item is either on the list or gone. Each row (`itemRow()`) is a coloured background layer plus a foreground layer that `maakSwipebaar()` drags with pointer events (`touch-action: pan-y` keeps vertical scrolling). Right past the threshold calls `koop()` (bought), left calls `remove()` (deleted, no purchase); the circle left on the row (`button.koop`) also marks it bought, and the × deletes without swiping but is hidden on touch screens (`@media (hover: none) and (pointer: coarse)`). Each row is its own card showing the name, below it the quantity, who added it and when ("2 pakken · door Els · gisteren"; `datumKort()`: vandaag, gisteren, the weekday within a week, then "3 okt", with the year only when it differs). While a row is being dragged `render()` is postponed (`slepen` / `renderWacht`), otherwise a realtime event would rebuild the row under your finger. After either action `toonOngedaan()` shows an undo bar for 5 seconds. The hint about swiping above the list can be dismissed; that is remembered per device in `localStorage` under `bonusbuddy-veeguitleg`.

**Purchases.** `purchases` holds what was actually bought (`list_id`, `name`, `normalized_name`, `quantity`, `bought_by`, `bought_at`, plus `item_id`, `added_by`, `item_created_at` so undo can restore the item exactly). Members can select and delete (the × per row in the `aankopen` view, `verwijderAankoop()`); inserting and updating goes only through `security definer` RPCs: `buy_item` and `undo_purchase` here, and `save_receipt` and `fill_article_ids` for receipts (see "Receipts" and "Historic AH receipts"). `buy_item(p_item)` deletes the item and, only when `lists.counts_for_profile` is true, inserts the purchase in the same transaction; it returns the purchase id or null. `undo_purchase(p_purchase)` deletes the purchase and re-inserts the item. Undo without a purchase (deleted item, or a list that does not count) re-inserts the item from the client with its original id. `bought_by` is null for purchases migrated from old checked-off items. The `aankopen` view, opened with the row "Aankopen" below the items, lists the purchases of the current list (`loadAankopen()`, newest first, max 200) and is kept live by the same realtime channel; a DELETE event only carries the `id`. Rows that came from a receipt show the price paid (`price` minus `discount`) and, when there is no `item_id`, only the date.

**Members.** The header of the list view shows a circle with the initial of each member (`leden-knop`), which toggles `leden-paneel` above the add form (`toonLedenPaneel()`) with who is in the list. `renderLeden()` renders both from the module-level `leden` array (names come from `namen`). `loadLeden()` runs alongside `loadItems()`, and the realtime channel refetches on a `list_members` INSERT and drops the row on DELETE. Only the creator sees "Verwijderen" per member (the `remove_member` RPC) and "Beheerder maken" / "Geen beheerder meer" (`set_member_manager`, stored in `list_members.is_manager`); a realtime UPDATE on `list_members` refetches the members.

**Invitations.** There is no fixed invite code any more. Only the creator and the managers (`can_invite()`, mirrored in the client by `magUitnodigen()`) see the invite button (`uitnodig-knop`). It calls `create_invite(p_list)`, which stores a row in `list_invites` (token, 7 days valid, single use) and returns the token; the client shows the link `…?uitnodiging=<token>` in the panel with a "Delen" button (`navigator.share`, or copy to the clipboard). `list_invites` has no policies or grants: it is only touched by the RPCs. Opening the link stores the token in `localStorage` under `bonusbuddy-uitnodiging` and removes it from the address bar; `route()` then calls `verwerkUitnodiging()`, which runs `join_list(p_code)` once you are logged in and opens that list. `join_list` deletes the invitation when someone joins with it (not when you already were a member). Removing a member or taking away the manager role deletes the invitations that person still had open. The invited person needs an account (signups are disabled). When your own membership disappears (removed by the creator, or the list is gone or archived), `verlaatLijst()` closes the list and returns to the overview. The DELETE handler checks `list_id` itself rather than trusting the channel filter.

**Security lives in the database, not the client.** The anon key is public by design. Every table has RLS enabled, and all policies go through `is_member(list_id)`. `lists` and `list_members` have select policies only: the client cannot insert into them directly. Creating, joining, changing and archiving lists goes through the `security definer` RPCs `create_list`, `join_list`, `create_invite` (creator and managers), `set_list_profile`, `remove_member` and `set_member_manager` (both creator only) and `archive_list` and `delete_list` (both creator only; deleting cascades to items, purchases, receipts and memberships), which is why `app.js` uses `db.rpc(...)` for those and plain table queries only for `items`, `profiles` and reading or deleting `purchases`. `receipts` is select-only too; it is written by `save_receipt`. `products`, `product_aliases` and `product_merges` are select-only as well and written by the product RPCs (see "Products"). `profiles` (one row per user, `display_name`) is writable only for your own row and readable by yourself and by people you share a list with. A new table or a new client-side write needs a matching policy or RPC in a new migration, and tables that should sync live must be added to the `supabase_realtime` publication.

**Products.** A product is a set of names. `products` (`id`, `name`) and `product_aliases` (`normalized_name` primary key → `product_id`) form a layer on top of `items` and `purchases`: those tables keep their own names and never store a product id, the link always runs through `normalized_name`. The trigger function `ensure_product()` on `items` and `purchases` (insert, or update of `name`) turns an unknown name into its own product, so adding an item needs no extra step. Merging is admin-only. The admin role is a row in `admins`, checked by `is_admin()` inside the write RPCs `merge_products(p_source, p_target)`, `undo_merge(p_merge)` and `rename_product(p_product, p_name)` and `set_product_profile(p_product, p_counts)`; the button in the UI is only a convenience. `merge_products` moves all aliases of the source to the target, deletes the source and logs it in `product_merges` (`source_id`, `source_name`, `aliases`); `undo_merge` restores the source with the same id, name and profile flag and refuses when the target has itself been merged since. `merge_products_internal` does the work without the role check and has `execute` revoked for the app roles: it exists for bulk merges from the SQL Editor. Merge rule: a product is the level at which a buyer switches for an offer. Brands of the same kind of product are merged ("heinz ketchup" into "ketchup"), as are packaging, spelling and typos; variants you do not switch between stay separate (halfvolle/volle melk, cola/cola zero). The original names stay in `items`, `purchases` and `product_aliases`, so brand information is not lost. The full rules, the fixed products (brood, stokbrood, pizza, kwark, …) and the open questions are in `docs/productregels.md`; record new decisions there. Only store brands are dropped from the names themselves, when a receipt is read (`INSTRUCTIES` in `bon-uploaden`, the `^ah` fallback in `ah-importeren.py`, and by hand in `data/ah-namen.json`); A-brands stay in the name. There is no brand list in the database. Non-admins can only select the aliases whose name occurs in an item or purchase they can see, and the products behind those. The `producten` view (`toonProducten()`, opened from `profiel` with "Producten beheren", `profielOpen` stays set) reads everything through `product_overview()`, which returns one JSON list with names and purchase counts across all lists; `samenvoegBron` holds the product being merged, the next tap picks the target.

**Purchase profile.** The section "Aankoopprofiel" in the `profiel` view shows what the household buys. The database does all the arithmetic: `loadAankoopprofiel()` calls the `security definer` RPC `purchase_profile(p_period, p_list)` (`'4w'`, `'3m'`, `'12m'` or `'alles'`, rolling from today; one list or null for all) and `renderAankoopprofiel()` only displays the JSON it returns. It counts purchases from lists you are a member of with `counts_for_profile`, archived ones included, and it is a household profile: everything bought on the list, also before you joined. A purchase's name is resolved to a product through `product_aliases`. `products.counts_in_profile` (default true) is the flag "telt niet mee in profiel" for things like a carrier bag, set by the admin with the switch in the `producten` view through `set_product_profile`: flagged products are left out of the purchase count, the product count and the top 10, but stay in spent and saved. `price` is the whole line before discount, so spent is `price - discount` and saved is `discount`, over purchases with a price only. The top 10 is ordered by purchase days in the period; the interval per product is the median gap between purchase days over all data (the list filter applies, the period does not), shown from 3 purchase days. Stores come from the receipt (`receipts.store`, grouped case-insensitively; none is "onbekend"). The month bars always cover the last 12 months. The key figures are always visible; the top 10, stores, months and the explanation "Hoe wordt dit berekend?" are `<details class="ap-blok">` blocks, collapsed by default. All days and months are Europe/Amsterdam. The bars are plain CSS (`staafRij()`), no chart library. `profielVraag` makes a late answer harmless. `docs/aankoopprofiel-controle.sql` holds a check query per figure for the SQL Editor.

**Deals.** `deals` holds supermarket offers (`supermarkt` AH/PLUS, `productnaam`, `omschrijving`, `prijs`, `geldig_van`, `geldig_tot`). For now it is filled by hand with test data from `seed_deals.sql` (which empties the table first); fetching real offers comes later and writes with the service role. Authenticated users can only select; there are no write policies or grants. The client never reads `deals` directly: `loadDeals()` calls the `security invoker` RPC `deals_for_list(p_list)`, which matches each item's `normalized_name` (generated column, `lower(trim(name))`) against currently valid deals with pg_trgm's `strict_word_similarity` and returns `(item_id, supermarkt, aantal)`. The threshold (`0.35`) is the single sensitivity knob and lives in that function. `loadDeals()` runs after `loadItems()`, after your own insert and on a realtime item INSERT; `itemRow()` shows a "Bonus" label with the stores below it (`dealWinkels()`, full names from `WINKELS`), and `renderBonus()` shows in the header how many products on the list have an offer. The offer text itself ("2e halve prijs") and the amount saved are not returned by the RPC, so they are not shown.

**Photo.** "Foto toevoegen" under the add form opens a file input (`accept="image/*"`, no `capture`, so the phone offers camera or library). `leesFoto()` shrinks the image on a canvas (`verkleinFoto()`, longest side `FOTO_MAX`, JPEG) and calls the Edge Function `foto-naar-items` through `db.functions.invoke`. The function checks the session itself with `auth.getUser` (it is deployed without JWT verification), sends the image to the Claude API with a JSON schema as output format and returns `{ producten: [{ naam, hoeveelheid }] }`, or `{ fout }` with a Dutch message. The rules for turning recipe ingredients into groceries (no cooking measures, skip `IN_HUIS`) live in `INSTRUCTIES` in the function; the model is the constant `MODEL`. The function writes nothing: the `foto` view lets you untick and edit the products, and the client then inserts them into `items` in one call under the normal RLS policy. `route()` checks `fotoOpen` a second time after `loadLijsten()`, because returning from the camera fires an auth event just before the chosen photo arrives. `fotoVraag` makes a late answer after cancelling harmless. The Anthropic key exists only as a Supabase secret.

**Receipts.** "Bon scannen" in the `aankopen` view (hidden when the list does not count for the profile) works like the photo flow, but the file input is `multiple`: `startStapel()` puts every chosen file in the module-level `bonStapel` (max `BON_MAX`), and `leesVolgende()` reads them in the background, `BON_TEGELIJK` at a time. `leesBon(bon)` shrinks the image with `verkleinFoto()` (a pdf, e.g. the digital receipt from the AH app, is sent as is by `leesBonBestand()`) and calls the Edge Function `bon-uploaden`, which returns `{ bon: { supermarkt, datum, totaal, regels: [{ bon_naam, naam, aantal, prijs, korting }] } }` or `{ fout }`. `naam` is the readable product name the model makes from the receipt text; the rules live in `INSTRUCTIES` in the function. Nothing is written and the photo is not stored anywhere. One file opens the `bon` view directly; several open the `stapel` view ("Bonnen controleren"), an overview with per receipt its state (`status`: `wacht`, `lezen`, `klaar`, `fout`, `opgeslagen`) and what `bonTwijfels()` finds odd about it (store, date or total missing, lines not adding up to the total, a line without a price, duplicate receipt in the database or in the stack, lines that match a purchase of that day, lines that only resemble an item on the list). Tapping a read receipt opens it in the `bon` view (`bonHuidig`; the header inputs write straight into that stack entry, so edits survive going back). "Alles zonder bijzonderheden opslaan" saves the receipts without doubts one by one and re-runs `controleerBon()` right before each, so a receipt that became a duplicate through the one just saved stays behind for review. The stack lives in memory only: `leegStapel()` drops it on list switch and logout, and `bonVraag` makes late answers harmless. While it holds unsaved receipts the `aankopen` view shows "Bonnen controleren (n)"; `aankopenOpen` stays set in both views, so `route()` leaves them alone. The `bon` view lets you correct store, date, total and lines; `controleerBon(bon)` calls `receipt_exists` (same store, date and total already saved: warning plus a confirm on save) and `match_receipt_lines`, which finds for each line the most similar purchase of the same day with pg_trgm like the deals, but with its own threshold (`0.5`), and `match_receipt_items` (see below). Saving (`bewaarBon()`) goes through `save_receipt(p_list, p_store, p_date, p_total, p_lines)`, which refuses lists that do not count for the profile. A product counts once per day per name and article id: a line linked to an existing purchase fills in `receipt_id`, `receipt_name`, `price`, `discount` and `article_id` on that row instead of adding one; a line linked to a purchase that already has receipt data, or with exactly the same name as a purchase of that day, is skipped, unless both have an `article_id` and they differ (two sizes with the same receipt text are two purchases). `purchases.article_id` (text) is the article number on the receipt, in the system of the supermarket on that receipt (`receipts.store`); for AH that is the `hqId`, not the webshop id. Only the AH import sends it: a scanned photo has no article number, so the app never does. New rows get the receipt date at 12:00 Amsterdam time as `bought_at`. A receipt also takes items off the list: `match_receipt_items(p_list, p_date, p_names)` (`security definer`, because a member may not read the alias of a new receipt name yet) finds per line the best item that was added on or before the receipt date (Amsterdam days) and returns `zeker` when it is the same name or the same product through `product_aliases`, otherwise it only passed the pg_trgm threshold (`0.5`). The `bon` view shows it in the same row as the purchase link (`toonKoppel()`; a line linked to a purchase of that day gets no item, `lijstItem()`): the same product is ticked by default, a look-alike only when the user ticks it (`regel.itemAan`, `vanLijst()`), and an undecided look-alike is a doubt in `bonTwijfels()`, so the stack never removes it on its own. `save_receipt` gets the `item_id` per line, checks the date again, deletes the item and inserts the purchase like `buy_item` does (item name, `item_id`, `added_by`, `item_created_at`) with the receipt data, in the same transaction; it counts them as `van_lijst`. Deleting the receipt later keeps that purchase and does not put the item back. `receipts` (`store`, `receipt_date`, `total`) only exists to recognise duplicate receipts. One photo per receipt. "Gescande bonnen" in the `aankopen` view opens the `bonnen` view (`toonBonnen()`; `aankopenOpen` stays set): the receipts of the list, each expandable to the purchases that carry its `receipt_id`, and a × that calls `delete_receipt(p_receipt)`. That RPC deletes the purchases that only came from the receipt (`item_id` is null), clears the receipt columns (including `article_id`) on purchases that were linked, and removes the receipt. `receipts` is not in the realtime publication; the view refetches when opened.

**Historic AH receipts.** Two scripts outside the app, both run by hand. `scripts/ah-bonnen` (Go, uses the `appie-go` library and the login tokens that the `ah-mcp` MCP server stores) only reads from the AH account and writes all receipts with their lines to `data/ah-bonnen.json`; `data/` is not in git. `scripts/ah-importeren.py` (Python, standard library only) logs in to Supabase with the app's email and password and stores them through the same RPCs as "Bon scannen" (`receipt_exists`, `match_receipt_lines`, `save_receipt`), so re-running adds nothing twice. Without `--echt` it is a dry run. AH only gives the abbreviated receipt text; `data/ah-namen.json` maps each text to a readable name, and lines that get the same name and the same `product_id` are merged. Discounts come per receipt and are matched to lines by name (`past()`), the ones that fit no line are dropped. The product id on a receipt is not a webshop id but AH's `hqId`, which every bonus article carries next to its webshop id; the import sends it as `article_id`. `scripts/ah-artikel-aanvullen.py` (dry run without `--echt`, reuses `ah-importeren.py`) fills `article_id` on AH purchases imported before that: it finds the receipt in `data/ah-bonnen.json` by date and total and the line by `receipt_name`, and writes through the `security definer` RPC `fill_article_ids(p_rows)`, which only touches purchases with a receipt in your lists and never overwrites an id.

**AH bonus exploration.** `scripts/ah-bonus` (Go, `appie-go` with an anonymous token, no account) writes the current bonus week to `data/ah-bonus.json`: per offer the discount text and labels, validity, and its articles with `webshop_id`, `hq_id`, title, brand, size and category. `scripts/ah-bonus-vergelijken.py` (Python, standard library, reuses `ah-importeren.py`) lays that next to `data/ah-bonnen.json` and counts which offers hit something we buy, by id and by name; `--producten` logs in as admin and uses the merged products from `product_overview()`. Both only read. The findings are in `docs/verkenning-ah-bonus.md`.

**Service worker.** `sw.js` is network-first with a cache fallback, same-origin GET only, so Supabase and CDN requests are never cached. When adding a new static file, add it to `ASSETS`; bump the `CACHE` name to evict old caches.

## Wensen

In bouwvolgorde:

1. Gedeelde boodschappenlijst voor mij en mijn vriendin, wijzigingen direct zichtbaar bij de ander
2. Items toevoegen, afstrepen en verwijderen
3. Zien wie een item heeft toegevoegd
4. Kortingen van supermarkten tonen bij items op de lijst
5. Items naar rechts swipen = gekocht (met datum en wie), naar links = verwijderd. Ook bruikbaar zonder swipen.
6. Een tabel met aankopen als basis voor het aankoopprofiel, alleen voor lijsten die meetellen voor het profiel
7. Alle onderdelen (lijstitems, aankopen, bonregels, aanbiedingen) koppelen aan hetzelfde product via zoekwoorden
8. Items groeperen per afdeling
9. Een lijst vullen vanuit een foto of screenshot (bijv. ingrediënten van een recept)
10. Kassabonnen scannen om aankopen toe te voegen, ook historische bonnen in bulk
11. Op basis van patronen gericht kortingsadvies geven

## Werkwijze

Leg bij elke wijziging kort uit wat je doet en waarom, in het Nederlands.

Elke databasewijziging is een nieuw migratiebestand in `supabase/migrations/`, nooit meer losse SQL in het dashboard. Hoe de database er nu uitziet lees je uit die map. De commando's staan in `docs/migraties.md`.
