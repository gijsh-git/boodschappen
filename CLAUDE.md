# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"BonusBuddy" (folder and repo are still called `boodschappen`) is a shared grocery-list PWA for a household (two partners sharing one list). It is a static site with no build step, no package manager, no tests and no linter: plain HTML/CSS/JS talking directly to Supabase from the browser. All UI text, code comments, SQL policy names and CSS variable names are in Dutch; keep new ones in Dutch.

## Running

There is nothing to build. Serve the directory over HTTP (the service worker and Supabase auth redirect do not work from `file://`):

```sh
python3 -m http.server 8000
```

Before the app does anything useful:

1. The database is defined by the migrations in `supabase/migrations/`. For a fresh project: `supabase link --project-ref <ref>` and `supabase db push`. The first migration is a baseline dumped from the live database.
2. Fill in `SUPABASE_URL` and `SUPABASE_ANON_KEY` in `config.js`. While the URL still contains the `JOUW-PROJECT` placeholder, `init()` in `app.js` stops at the login view with a "fill in config.js" message.
3. The origin you serve from must be an allowed redirect URL in Supabase Auth, since invite and password-reset mails link back to `location.origin + location.pathname`.
4. For "Foto toevoegen": deploy `supabase/functions/foto-naar-items/index.ts` as Edge Function `foto-naar-items` with "Verify JWT" off (dashboard editor, or `supabase functions deploy foto-naar-items --no-verify-jwt`) and set the secret `ANTHROPIC_API_KEY`. "Bon scannen" needs `supabase/functions/bon-uploaden/index.ts` deployed the same way as Edge Function `bon-uploaden`; it uses the same secret. The weekly offers need `supabase/functions/aanbiedingen-opslaan/index.ts` as Edge Function `aanbiedingen-opslaan`, also with "Verify JWT" off, and the secret `AANBIEDINGEN_SLEUTEL` (a long random value, e.g. `openssl rand -hex 32`; the same value is a repository secret in GitHub, see "Offers"); `supabase/functions/artikelen-classificeren/index.ts` and `supabase/functions/term-classificeren/index.ts` are deployed the same way under those names and use both that secret and `ANTHROPIC_API_KEY`. For the second one the database needs the address and the key in Vault, once, in the SQL Editor: `select vault.create_secret('https://<ref>.supabase.co/functions/v1/term-classificeren', 'term_classificeren_url');` and `select vault.create_secret('<value of AANBIEDINGEN_SLEUTEL>', 'aanbiedingen_sleutel');`. The functions are not part of the GitHub Pages deploy: after changing one, deploy it again.

The app is hosted on GitHub Pages from `main` (https://gijsh-git.github.io/boodschappen/), so pushing to `main` deploys.

## Architecture

**Load order matters.** `index.html` loads five classic scripts in order: supabase-js v2 from the jsDelivr CDN (global `supabase`), `config.js` (sets `window.CONFIG`), `data.js` (global `Data`, all Supabase calls, see `ARCHITECTURE.md`; `app.js` calls `Data.init(url, key)`, which creates the client), `logica.js` (global `Logica`, state and rules without DOM; for now the favourites, Voor jou, the deals on the list and the screen "Koppelingen"), then `app.js`. There are no modules or imports. Every Supabase call lives in `data.js`: tables, RPCs, auth, the Edge Functions and the live channel (`Data.volgLijst()` / `Data.stopVolgen()`, which hands the Supabase messages to handlers in `subscribe()`). `app.js` contains no `db.` any more; where this file names a Supabase call (`db.rpc(...)`, `signInWithPassword`, `db.functions.invoke`), it is made by the matching function in `Data`. The rest of the logic still lives in `app.js` and moves to `logica.js` part by part (see `ARCHITECTURE.md`).

**Views.** `index.html` holds sixteen `<section id="view-…">` elements (`login`, `forgot`, `sent`, `password`, `naam`, `profiel`, `producten`, `voorjou`, `setup`, `nieuw`, `list`, `aankopen`, `foto`, `bon`, `bonnen`, `stapel`); `show()` toggles their `hidden` attribute. Flow: `init()` → session check → `route()` fetches the user's `profiles` row (none yet → `naam` view to enter a display name once; it can be changed later in `profiel`, opened from the tab bar: the header shows your initial, name and e-mail address with a pencil button to edit the name, below it the purchase profile (see "Purchase profile"), "Mijn favorieten" (see "Favourites") and a menu "Account" with "Koppelingen beheren" (admin only) and "Uitloggen") → `loadLijsten()` fetches all the user's `list_members` rows into the module-level arrays `lijsten` (active) and `archief` (archived) → either `setup` (no lists yet) or `openList()` on the last opened list (id remembered in `localStorage` under `bonusbuddy-lijst`, falling back to the first list).

**Multiple lists.** The `setup` view is the overview "Mijn lijsten": it lists your lists (tap to switch) and is reachable from the list view by tapping the list name in the header (`lijsten-knop`). Its plus button opens the `nieuw` view, which holds the forms to create a list or join by pasting an invitation link. Each row has a switch "Meetellen voor aankoopprofiel", stored in `lists.counts_for_profile` (default true) through the `set_list_profile` RPC. The setting belongs to the list, so it is shared by all members; it only decides whether the list counts in the purchase profile (`purchase_profile` reads it); purchases are always stored (see "Purchases").

**Archiving and deleting.** Archiving is the normal way to get rid of a list, because deleting takes its purchases and receipts along (`on delete cascade`), and those are the basis of the purchase profile. The creator sees "Lijst archiveren" per row and, right of it, a bin button that calls `delete_list` after a confirm that warns about this (`verwijderLijst()`). Archiving calls `archive_list(p_list, p_archived)` and sets `lists.archived_at`. Archived lists leave the overview and show up in the collapsible block "Gearchiveerd" below it (`archiefRij()`), where the creator can put them back with "Terugzetten". Nothing can be added to an archived list: the insert policy on `items`, `join_list` and `save_receipt` all refuse it. Purchases and receipts stay and keep counting for the profile. A member who has the list open when it is archived is sent back to the overview by `verlaatLijst()`, triggered by the realtime UPDATE on `lists` or, after standby, by `controleerArchief()` in `loadItems()`.

`route()` runs again on every auth event (e.g. when the app returns to the foreground), so screens that must stay put set a flag it checks first: `naamOpen`, `profielOpen`, `voorjouOpen`, `lijstenOpen`, `aankopenOpen`, `fotoOpen`, `bonOpen`.

**Tab bar and back.** `<nav id="tabbalk">` (Lijst, Voor jou, Profiel) is fixed at the bottom; `show()` only shows it on the views in `TABS` (`list`, `setup`, `voorjou`, `profiel`) and marks the current tab. "Lijst" (`naarLijst()`) opens the overview "Mijn lijsten"; only when you have exactly one list it goes straight to that list. Sub-screens (`aankopen`, `bonnen`, `stapel`, `producten`, `nieuw`) have a round back button top left and `data-terug="<id of that button>"` on the section: `maakTerugveegbaar()` lets you swipe the screen to the right, which clicks that button. `foto` and `bon` keep "Annuleren" at the bottom and cannot be swiped away, because leaving them discards work.

**Voor jou.** Two parts. On top "Nu in de bonus": `loadAanbod()` calls `Logica.laadAanbiedingen()`, which keeps the JSON of `offers_for_me()` (see "Matching offers"); `aanbodRij()` shows per offer the discount text, title, store, last valid day and the reason (your favourite, or the regular products in it), with a plus that puts the offer itself on the open list under its title (`Logica.aanbiedingNaam()`, the title without the trailing asterisk), never the name of the regular product: `zetOpLijst(naam, aanbiedingId)` calls `add_offer_item` (see "Matching offers"). An offer that is already on the list (same name, or an item with its `offer_id`) shows "staat op de lijst" instead of the plus. Below it the household's regular products: `Logica.laadVoorJou()` calls `purchase_profile('3m', null)` and keeps its top 10. `Logica.voorJouOver()` leaves out what is already on the open list (same name, case-insensitive, or an item with the `offer_id` of an offer that contains the product) or was dismissed with "Niet nu" (`Logica.slaOver()`, in memory only) and sorts the product that is furthest past its usual interval (`om_de`) first; `renderVoorJou()` puts that one in the large card; `zetOpLijst()` inserts it into `items` of the open list under the product name, without article or product id.

**Auth is invite-only with passwords.** Signups are disabled in the Supabase dashboard; the owner adds people there with "Invite user". Login is `signInWithPassword`. "Wachtwoord vergeten?" goes `login` → `forgot` (request the mail) → `sent` (confirmation, with resend). Invite and reset mails land back on the app with `type=invite` / `type=recovery` in the URL hash, which `app.js` reads before it calls `Data.init()` to create the Supabase client (the client clears the hash). That sets `mustSetPassword`, which makes `route()` show the `password` view instead of the list until `updateUser({ password })` succeeds. Supabase's English auth errors are mapped to Dutch in `nl()`.

**Styling.** `styles.css` uses CSS variables with a dark-mode override, except the `.auth` screens (login, password), which pin the light values so they always look like the design. Fonts come from Google Fonts.

**State and sync.** `app.js` keeps a module-level `items` array as the single source of truth for rendering; `render()` rebuilds the `<ul id="items">` from it. Three things mutate it and must stay consistent:

- Local actions apply optimistically (`koop()`, `remove()`) and call `loadItems()` to resync if the Supabase write fails.
- A Supabase Realtime `postgres_changes` channel per list, filtered on `list_id`, applies INSERT/UPDATE/DELETE from the other user. Inserts are de-duplicated by `id` because your own insert arrives both from the `.insert().select()` response and from the realtime event.
- The same channel also listens to `list_members` (see "Members" below).
- A DELETE on `items` and `purchases` only carries the `id` (default replica identity), so Realtime cannot filter it on `list_id` and would not send it at all. `Data.volgLijst()` therefore listens to those two DELETEs without a filter, and the handlers in `subscribe()` ignore ids that are not in the open list. Do not put a `list_id` filter back on them.
- A `visibilitychange` handler refetches everything when the app returns to the foreground, since phones drop the realtime socket in standby.

**Swipe.** There is no checking off any more: an item is either on the list or gone. Each row (`itemRow()`) is a coloured background layer plus a foreground layer that `maakSwipebaar()` drags with pointer events (`touch-action: pan-y` keeps vertical scrolling). Right past the threshold calls `koop()` (bought), left calls `remove()` (deleted, no purchase); the circle left on the row (`button.koop`) also marks it bought, and the × deletes without swiping but is hidden on touch screens (`@media (hover: none) and (pointer: coarse)`). Each row is its own card showing the name, below it the quantity, who added it and when ("2 pakken · door Els · gisteren"; `datumKort()`: vandaag, gisteren, the weekday within a week, then "3 okt", with the year only when it differs). While a row is being dragged `render()` is postponed (`slepen` / `renderWacht`), otherwise a realtime event would rebuild the row under your finger. After either action `toonOngedaan()` shows an undo bar for 5 seconds. The hint about swiping above the list can be dismissed; that is remembered per device in `localStorage` under `bonusbuddy-veeguitleg`.

**Purchases.** `purchases` holds what was actually bought (`list_id`, `name`, `normalized_name`, `quantity`, `bought_by`, `bought_at`, plus `item_id`, `added_by`, `item_created_at` so undo can restore the item exactly). Members can select and delete (the × per row in the `aankopen` view, `verwijderAankoop()`); inserting and updating goes only through `security definer` RPCs: `buy_item` and `undo_purchase` here, and `save_receipt` and `fill_article_ids` for receipts (see "Receipts" and "Historic AH receipts"). `buy_item(p_item)` deletes the item and inserts the purchase in the same transaction, whether or not the list counts for the profile; it returns the purchase id, or null when the item was already gone. `undo_purchase(p_purchase)` deletes the purchase and re-inserts the item. Undo without a purchase (a deleted item) re-inserts the item from the client with its original id. `bought_by` is null for purchases migrated from old checked-off items. The `aankopen` view, opened with the row "Aankopen" below the items, lists the purchases of the current list (`loadAankopen()`, newest first, max 200) and is kept live by the same realtime channel; a DELETE event only carries the `id`. Rows that came from a receipt show the price paid (`price` minus `discount`) and, when there is no `item_id`, only the date.

**Members.** The header of the list view shows a circle with the initial of each member (`leden-knop`), which toggles `leden-paneel` above the add form (`toonLedenPaneel()`) with who is in the list. `renderLeden()` renders both from the module-level `leden` array (names come from `namen`). `loadLeden()` runs alongside `loadItems()`, and the realtime channel refetches on a `list_members` INSERT and drops the row on DELETE. Only the creator sees "Verwijderen" per member (the `remove_member` RPC) and "Beheerder maken" / "Geen beheerder meer" (`set_member_manager`, stored in `list_members.is_manager`); a realtime UPDATE on `list_members` refetches the members. Everyone except the creator sees "Lijst verlaten" per row in the overview (`lijstVerlaten()`, RPC `leave_list`, which also drops the invitations that person had open); the creator cannot leave and archives or deletes the list instead. The purchases stay on the list, but stop counting for the leaver's purchase profile.

**Invitations.** There is no fixed invite code any more. Only the creator and the managers (`can_invite()`, mirrored in the client by `magUitnodigen()`) see the invite button (`uitnodig-knop`). It calls `create_invite(p_list)`, which stores a row in `list_invites` (token, 7 days valid, single use) and returns the token; the client shows the link `…?uitnodiging=<token>` in the panel with a "Delen" button (`navigator.share`, or copy to the clipboard). `list_invites` has no policies or grants: it is only touched by the RPCs. Opening the link stores the token in `localStorage` under `bonusbuddy-uitnodiging` and removes it from the address bar; `route()` then calls `verwerkUitnodiging()`, which runs `join_list(p_code)` once you are logged in and opens that list. `join_list` deletes the invitation when someone joins with it (not when you already were a member). Removing a member or taking away the manager role deletes the invitations that person still had open. The invited person needs an account (signups are disabled). When your own membership disappears (removed by the creator, or the list is gone or archived), `verlaatLijst()` closes the list and returns to the overview. The DELETE handler checks `list_id` itself rather than trusting the channel filter.

**Security lives in the database, not the client.** The anon key is public by design. Every table has RLS enabled, and all policies go through `is_member(list_id)`. `lists` and `list_members` have select policies only: the client cannot insert into them directly. Creating, joining, changing and archiving lists goes through the `security definer` RPCs `create_list`, `join_list`, `create_invite` (creator and managers), `set_list_profile`, `remove_member` and `set_member_manager` (both creator only) and `archive_list` and `delete_list` (both creator only; deleting cascades to items, purchases, receipts and memberships), which is why `app.js` uses `db.rpc(...)` for those and plain table queries only for `items`, `profiles` and reading or deleting `purchases`. `receipts` is select-only too; it is written by `save_receipt`. `profiles` (one row per user, `display_name`) is writable only for your own row and readable by yourself and by people you share a list with. A new table or a new client-side write needs a matching policy or RPC in a new migration, and tables that should sync live must be added to the `supabase_realtime` publication.

**Purchase profile.** The section "Aankoopprofiel" in the `profiel` view shows what the household buys. The database does all the arithmetic: `loadAankoopprofiel()` calls the `security definer` RPC `purchase_profile(p_period, p_list)` (`'4w'`, `'3m'`, `'12m'` or `'alles'`, rolling from today; one list or null for all) and `renderAankoopprofiel()` only displays the JSON it returns. It counts purchases from lists you are a member of with `counts_for_profile`, archived ones included, and it is a household profile: everything bought on the list, also before you joined. A purchase counts under its product type through `purchase_types()` (the article on the receipt first, then the name; see "Product types"); a purchase without a type counts under its own name. `product_types.counts_in_profile` (default true) is the flag "telt niet mee in profiel" for things like a carrier bag, set with the switch in the opened type in the screen "Koppelingen" (`update_product_type()`): flagged types are left out of the purchase count, the product count and the top 10, but stay in spent and saved. `price` is the whole line before discount, so spent is `price - discount` and saved is `discount`, over purchases with a price only. The top 10 is ordered by purchase days in the period; the interval per product is the median gap between purchase days over all data (the list filter applies, the period does not), shown from 3 purchase days. Stores come from the receipt (`receipts.store`, grouped case-insensitively; none is "onbekend"). The month bars always cover the last 12 months. The key figures are always visible; the top 10, stores, months and the explanation "Hoe wordt dit berekend?" are `<details class="ap-blok">` blocks, collapsed by default. All days and months are Europe/Amsterdam. The bars are plain CSS (`staafRij()`), no chart library. `profielVraag` makes a late answer harmless. `docs/aankoopprofiel-controle.sql` holds a check query per figure for the SQL Editor.

**Favourites.** A favourite is something the user wants to hear about when it is on offer: a product type, a brand plus a type, or only a brand. The table stores what the user picked or typed, a term, a brand, or both (`favorites`: `user_id`, `term`, `brand`, `category`, plus the generated columns `normalized_term` and `normalized_brand`). They are per user, not per list: RLS only gives you your own rows, and the client writes the table directly (no RPC). The database refuses a row without term and brand and, through the unique index `favorites_uniek`, the same term and brand twice. `normalize_search(text)` (lower case, no accents through the `unaccent` extension, spaces collapsed) is the one normalisation for favourites; `Logica.zoekvorm()` mirrors it in the client. The section "Mijn favorieten" in the `profiel` view is the only place to add, edit (pencil, fills the form) and delete them. State and rules are in `logica.js` (`Logica.bewaarFavoriet()`, `verwijderFavoriet()`, `favorietSuggesties()`); `app.js` only renders (`renderFavorieten()`, `favorietRij()`) and handles the form. While typing, `suggest_favorite_terms(p_query)` (`security definer`, because the type list is not readable for the app roles) suggests product types by name, with the main group as `category` and the number of articles of the type as `articles`; `suggest_favorite_brands(p_query)` (`security invoker`) suggests brands from `articles.brand` ("AH" and "AH Excellent" are separate brands). `category` is only stored when the term was picked from the suggestions and is dropped when the term is changed afterwards (`favSuggestie`); there is no input for it, and it only counts for a term that stands for no type. What a term stands for is decided when matching, not stored: `offers_for_me()` resolves it with `name_type()`, so a correction by the admin or a merged type works through by itself ("tomatensoep" follows soep). A term that stands for a type hits every article of that type in an offer, also when the word is not in the title, and with a brand only that brand's articles within the type; a brand alone hits everything of the brand; a term that stands for nothing falls back to its words in the title plus the main category, as before. The full definition is in `ROADMAP.md`, step 4.

**Bonus label.** The "Bonus" label on the list comes from the real offers (the old `deals` table with test data and `deals_for_list` are gone; the names `loadDeals()` and `Logica.laadDeals()` remain): `loadDeals()` calls `Logica.laadDeals()`, which keeps the result per item (`Logica.dealsVan()`) and calls `offers_for_list(p_list)` (see "Matching offers"), returning `(item_id, supermarkt, aantal)`. `loadDeals()` runs after `loadItems()`, after your own insert and on a realtime item INSERT; `itemRow()` shows a "Bonus" label with the stores below it (`Logica.dealWinkels()`, full names from `WINKELS`), and `renderBonus()` shows in the header how many products on the list have an offer. The offer text itself ("2e halve prijs") and the amount saved are not returned by the RPC, so they are not shown.

**Offers.** `articles` (primary key `supermarket` + `article_id`, plus `webshop_id`, `title`, `brand`, `size`, `category`) holds every article ever seen in an offer and is never cleaned up: `article_id` means the same as `purchases.article_id` (for AH the `hqId`), so the table is also the translation from a receipt's article number to an article. `offers` (unique on `supermarket`, `offer_id`, `valid_from`) holds title, `discount_text`, `labels` (jsonb as the source gives them: code plus numbers), `discount_type` (code of the first label), `valid_from`/`valid_to`, `is_group` and `store_only`; `offer_articles` links the two and carries `price` and `bonus_price` of that week. Authenticated users can only select. Writing goes through `save_offers(p_supermarket, p_offers)`, executable by the service role only: it upserts articles and offers, replaces the articles of an offer (unless the offer has `complete: false`, a group whose articles could not be fetched), skips articles without an `article_id`, and deletes offers that expired more than 28 days ago (`c_bewaren`). The service role key never leaves Supabase: the Edge Function `aanbiedingen-opslaan` (deployed without JWT verification) compares the header `x-aanbiedingen-sleutel` in constant time with the secret `AANBIEDINGEN_SLEUTEL`, refuses bodies over 5 MB and then calls only `save_offers` with the service role from its own environment, returning its result. `scripts/ah-bonus-opslaan.py` (dry run without `--echt`) maps `data/ah-bonus.json` to that format and posts `{ supermarkt, aanbiedingen }` to the function with `AANBIEDINGEN_SLEUTEL` from the environment. `.github/workflows/ah-bonus.yml` runs `scripts/ah-bonus` and then that script every Monday and Thursday morning, with `AANBIEDINGEN_SLEUTEL` as a repository secret (the repo is public, so the service role key must never be stored there); GitHub switches off a schedule after 60 days without a commit in the repo. The app reads them only through the matching RPCs below.

**Matching offers.** Roadmap step 5, part 1. All matching is in Postgres. `settings` (`key`, `value`, `description`; no policies or grants, read only by the functions) holds the limit for a regular product: `regular_min_days` (3 purchase days) and `regular_max_age_days` (last purchase within 365 days); the admin changes them with an `update` in the SQL Editor. `regular_products(p_user)` returns the product types a household buys by that limit, on the same basis as `purchase_profile` (the column is still called `product_id`; it holds the type id). The link article → type is `article_types` (see "Product types"), without approval beforehand. `offers_for_me()` (`security definer`) returns the currently valid offers that count for you, each once, as JSON with `favorieten` (your favourites that hit an article in it, see "Favourites": by type when the term stands for one, otherwise the term as whole words in the title; the brand exact) and `producten` (regular types with an article in it, through `article_types`); favourites first, then by purchase days. `offers_for_list(p_list)` (`security definer`, guarded by `is_member`) gives per item the stores with a valid offer, through the item's name (`term_articles()`, see "Matching list terms": a type, a brand, a name of a type, or a look-alike) or through `items.offer_id`: the offer an item was put on the list with from Voor jou (set to null when the offer is cleaned up). That link is what gives an offer on the list its label when its title stands for no type, and it shows for every member. The regular-product limit does not apply there. `add_offer_item(p_list, p_offer)` (`security definer`, members only, refuses archived lists) is the only way an offer gets on a list: it inserts a new item named after the offer title (fixed from then on; always a separate row, also when the same product is already on the list) with `offer_id`, `article_supermarket` + `article_id` (only when the offer has exactly one article) and `type_id`: the type when all articles of the offer that have a type share one. In that case, and when the title stood for nothing yet, the title also becomes a name of that type in `term_synonyms` (source `catalog`), so the purchase later counts under the type in the profile. Nothing is merged any more. `items.type_id` is a record only: the label runs through the name or the offer. `undo_purchase` does not restore the offer, article or type; undoing a delete does (`Data.zetItemTerug()`). `offer_details_for_list(p_list)` (same routes, `security definer`) returns per item and offer what exactly is on offer: title, discount text, last valid day and up to 6 article titles with the total. The green bar in the header of the list (`bonus-balk`, a button) toggles `bonus-paneel` (`toonBonusPaneel()`), which shows them (`Logica.laadDealDetails()`, `bonusDetailRij()`); it is fetched when the panel opens and again when the labels reload while it is open.

**Matching list terms.** For the Bonus label only. `term_match(p_name)` says what a typed term stands for, as one row `(step, type_id, brand_key)` or no row when it matches nothing; the first layer with a hit wins: the name of a type (step 1; curated, always first), a brand (`articles.brand_key`, step 3: whoever types exactly a brand means everything of that brand, even when the name hangs on one type for the profile), a name in `term_synonyms` (step 2; with `brand_key` it means that brand within the type, and a row without a type means judged and belonging nowhere: a row, no articles), the same after Dutch stemming (`stem` on `product_types` and `term_synonyms`, from `list_stem`), a brand plus a kind in either order ("nivea shampoo", "tandpasta oral b": one part is a brand, the other resolves through `name_type()`; step 3 with both), and tolerant (step 4: pg_trgm `similarity` against type names, names and brands, only the best, from `fuzzy_min_similarity_pct` in `settings` and from 5 characters). The title layer is gone. `term_articles(p_name)` (same signature as before: `supermarket` in upper case, `article_id`, `step`) turns that into articles: all articles of the type, all articles of the brand, or the brand's articles within the type (falling back to the whole type when there are none), over all articles ever seen. `name_type(p_name)` is the type of a name for receipts and items: type name, then `term_synonyms`, then the stems; no brand layer and not tolerant, so a purchase "fanta" is sinas while the label for "fanta" covers everything of Fanta. `match_key(text)` is `normalize_search` with everything but letters and digits removed ("proteine drank" equals "proteinedrank"). `offers_for_list` and `offer_details_for_list` have two routes: the item's name through `term_articles()`, and `items.offer_id`. A term that stands for nothing goes to `handle_unmatched_term(p_name)`, the single point for unmatched terms, called by the trigger `items_term` (`check_item_term()`, insert or update of `name`, not for items with an `offer_id`; a known term without articles is not unmatched; an error there only raises a warning, so it never blocks adding an item). It upserts `unmatched_terms` (`key`, `term`, `times`, `first_seen`, `last_seen`, `claimed_at`, `judged_at`; no user or list) and then kicks the Edge Function `term-classificeren` through `pg_net` (`kick_term_classifier()`, which reads the function's address and the key from Supabase Vault under the names `term_classificeren_url` and `aanbiedingen_sleutel`; without them it does nothing; the request leaves after the commit). The function (no JWT verification, same header and secret as `aanbiedingen-opslaan`, model in `MODEL`) claims the open terms with `term_work(p_limit)`, asks the Claude API per term for a type name from the list or "geen type" plus the brand when the term names one, and stores the outcome with `save_term_judgments(p_rows)` (both service role only): a name in `term_synonyms` with source `ai` and the date, no approval beforehand, `judged_at` on the term, and `type_id` on the items with that name. That update arrives through Realtime, and the item UPDATE handler in `subscribe()` calls `loadDeals()` when `type_id` or the name changed, so the label appears for every member within seconds. The claim keeps a photo with many unknown items from judging the same terms more than once; a failed call leaves the terms open and they are picked up again after 3 minutes or by the weekly run (`scripts/ah-bonus-opslaan.py` calls the function too). The trigger `purchases_term` (`check_purchase_term()`) sends a purchase name without a type along the same point (a new receipt name, or an item that only matched tolerantly); a bare brand name stays without a type. A term judged without a type is never judged again. The helper functions have `execute` revoked for the app roles. The decisions are in `docs/productregels.md`; `docs/producttypes-controle.sql` holds check queries.

**Product types.** The catalogue with merging has been replaced by a fixed list of product types with automatic classification; the phases are in `ROADMAP.md`, step 5 part 4. Since 9 October 2026 the profile, Voor jou, the Bonus label and the favourites run on types, and the old model is gone: the tables `products`, `product_aliases`, `product_merges`, `article_links`, `article_link_rejections` and `article_names`, their RPCs and the trigger `ensure_product()` were dropped in the migration `oude_catalogus_weg` (their last contents are in `data/backup/20261009-oude-catalogus.json`, not in git). There is no merging of names any more and nothing waits for approval. `product_types` (`name`, generated unique `key` through `match_key`, generated `stem`, `main_group`: the supermarket's main category or "Geen boodschappen", `scope`, `excludes`, `counts_in_profile`) has no policies or grants. A type is the level where a buyer switches for an offer (`docs/productregels.md`). **The database is the source of the type list.** Types are created with `create_product_type(p_name, p_main_group, p_scope, p_excludes, p_counts, p_suggestion)` (terms and articles without a type whose `suggested_type` equals `p_suggestion` get the new type at once, the other untyped articles are judged again), changed with `update_product_type(p_type, …)` (after a rename the old name keeps working as a name of the type) and merged with `merge_product_types(p_source, p_target)` (by name: moves the articles, names and items of the source, deletes it and keeps its name as a name of the target); all admin only, from the screen "Koppelingen". `docs/producttypes-export.csv` is a printout, never an input: `scripts/producttypes-exporteren.py` rewrites it from the database through the Edge Function `producttypes-exporteren` (no JWT verification, same header and secret as `aanbiedingen-opslaan`; reads `product_types_export()`, service role only) with `AANBIEDINGEN_SLEUTEL` from the environment or `.env`, without a login, and `.githooks/pre-commit` runs it on every commit and adds the file (enable once per clone with `git config core.hooksPath .githooks`; when reading fails the commit continues with a warning). The file holds only the types, not the names that belong to them (what people typed or bought; the repo is public) and no article counts (they change every bonus week). Never edit it by hand and never load types from a file. The first list was proposed by the AI from the old catalogue and reviewed by the admin on 8 October 2026; the scripts for that one-off (`producttypes-voorstellen.py`, `producttypes-laden.py`, `naar-producttypes.py`) were removed on 9 October 2026 and are in the git history, as is the old `docs/producttypes.csv`. `save_term_types()` and `set_article_types()` (admin only) are what the screen uses to correct a name or an article (source `manual`). `article_types` (primary key `supermarket` + `article_id`, `type_id` or null for "no type" with `suggested_type`, `confidence`, `reason`, `source` `ai`/`receipt`/`catalog`/`manual`, `judged_at`, `reviewed_at`; no policies or grants) holds the type of an article. The Edge Function `artikelen-classificeren` (no JWT verification, same header and secret as `aanbiedingen-opslaan`, model in `MODEL`) reads `article_type_work(p_limit)` (articles without a row, or without a type while types were added since `judged_at`; plus the whole type list in a fixed order for prompt caching), asks the Claude API per `PORTIE` articles (`TEGELIJK` portions at once) for a type name from the list or "geen type", and writes through `save_article_types(p_rows, p_judged_at)`, which only replaces unreviewed `ai` rows; both RPCs are service role only. `scripts/ah-bonus-opslaan.py --echt` calls it after saving until nothing is left (`--types` does only that), so new articles get a type in the same run as the weekly fetch. `term_synonyms` is the one table name → type (`type_id`, null meaning judged without a type, then with `suggested_type` for the type the AI misses; `brand_key`, `confidence`, `reason`, `reviewed_at`, generated `stem`; `source` is `manual`, `ai` or `catalog`, in that order of precedence). `save_term_types_internal(p_rows, p_source)` writes it without a role check (for the Edge Function and `add_offer_item`); a term that is itself a type name never gets a row, because the type name wins. `set_article_types(p_rows, p_source)` sets the type of an article and marks it reviewed. `purchase_types()` (service role only) derives the type of a purchase, never stored: the article on the receipt first, then the name. `docs/producttypes-controle.sql` holds check queries (what has a type, what does not, what the AI could not place). The screen "Koppelingen" (the `producten` view, `toonKoppelingen()`, opened from `profiel` with "Koppelingen beheren", admin only, `profielOpen` stays set) is where the admin checks and corrects what the AI linked; nothing waits for approval. Three collapsible blocks show what needs attention: "Termen" (AI-judged terms, newest first), "Artikelen om na te kijken" (per type, with "Alles klopt") and "Geen type" (grouped on the type the AI misses, with "Type aanmaken" and "Geen type nodig"); below them the searchable list of all types, each opening to a form (name, main group, scope, the switch "Telt mee in aankoopprofiel"), "Samenvoegen met een ander type" and its names and articles. Every row has "Klopt", "Ander type" (one search-as-you-type picker, `kpKiezer()`, reused everywhere) or "Geen type". State and rules are in `logica.js` (`Logica.laadKoppelingen()`, `artikelGroepen()`, `ontbrekend()`, `zoekTypes()`, `klopt()`, `zetTermType()`, `zetArtikelType()`, `maakType()`, `wijzigType()`, `voegTypesSamen()`; every action refetches the overview); `app.js` only renders (`renderKoppelingen()`, the `kp…` functions). `type_link_overview()` returns the AI-judged terms not yet reviewed, the articles judged with confidence medium or low not yet reviewed, the articles without a type, and all types with their counts; `type_details(p_type)` the names and articles of one type; `mark_links_reviewed(p_terms, p_articles)` only sets `reviewed_at`. `reset_untyped_articles()` now also kicks `artikelen-classificeren` through `pg_net` (address in Vault under `artikelen_classificeren_url`).

**Photo.** "Foto toevoegen" under the add form opens a file input (`accept="image/*"`, no `capture`, so the phone offers camera or library). `leesFoto()` shrinks the image on a canvas (`verkleinFoto()`, longest side `FOTO_MAX`, JPEG) and calls the Edge Function `foto-naar-items` through `db.functions.invoke`. The function checks the session itself with `auth.getUser` (it is deployed without JWT verification), sends the image to the Claude API with a JSON schema as output format and returns `{ producten: [{ naam, hoeveelheid }] }`, or `{ fout }` with a Dutch message. The rules for turning recipe ingredients into groceries (no cooking measures, skip `IN_HUIS`) live in `INSTRUCTIES` in the function; the model is the constant `MODEL`. The function writes nothing: the `foto` view lets you untick and edit the products, and the client then inserts them into `items` in one call under the normal RLS policy. `route()` checks `fotoOpen` a second time after `loadLijsten()`, because returning from the camera fires an auth event just before the chosen photo arrives. `fotoVraag` makes a late answer after cancelling harmless. The Anthropic key exists only as a Supabase secret.

**Receipts.** "Bon scannen" in the `aankopen` view works like the photo flow, but the file input is `multiple`: `startStapel()` puts every chosen file in the module-level `bonStapel` (max `BON_MAX`), and `leesVolgende()` reads them in the background, `BON_TEGELIJK` at a time. `leesBon(bon)` shrinks the image with `verkleinFoto()` (a pdf, e.g. the digital receipt from the AH app, is sent as is by `leesBonBestand()`) and calls the Edge Function `bon-uploaden`, which returns `{ bon: { supermarkt, datum, totaal, regels: [{ bon_naam, naam, aantal, prijs, korting }] } }` or `{ fout }`. `naam` is the readable product name the model makes from the receipt text; the rules live in `INSTRUCTIES` in the function. Nothing is written and the photo is not stored anywhere. One file opens the `bon` view directly; several open the `stapel` view ("Bonnen controleren"), an overview with per receipt its state (`status`: `wacht`, `lezen`, `klaar`, `fout`, `opgeslagen`) and what `bonTwijfels()` finds odd about it (store, date or total missing, lines not adding up to the total, a line without a price, duplicate receipt in the database or in the stack, lines that match a purchase of that day, lines that only resemble an item on the list). Tapping a read receipt opens it in the `bon` view (`bonHuidig`; the header inputs write straight into that stack entry, so edits survive going back). "Alles zonder bijzonderheden opslaan" saves the receipts without doubts one by one and re-runs `controleerBon()` right before each, so a receipt that became a duplicate through the one just saved stays behind for review. The stack lives in memory only: `leegStapel()` drops it on list switch and logout, and `bonVraag` makes late answers harmless. While it holds unsaved receipts the `aankopen` view shows "Bonnen controleren (n)"; `aankopenOpen` stays set in both views, so `route()` leaves them alone. The `bon` view lets you correct store, date, total and lines; `controleerBon(bon)` calls `receipt_exists` (same store, date and total already saved: warning plus a confirm on save) and `match_receipt_lines`, which finds for each line the most similar purchase of the same day with pg_trgm, with its own threshold (`0.5`), and `match_receipt_items` (see below). Saving (`bewaarBon()`) goes through `save_receipt(p_list, p_store, p_date, p_total, p_lines)`, which refuses archived lists (it works on lists that do not count for the profile too). A product counts once per day per name and article id: a line linked to an existing purchase fills in `receipt_id`, `receipt_name`, `price`, `discount` and `article_id` on that row instead of adding one; a line linked to a purchase that already has receipt data, or with exactly the same name as a purchase of that day, is skipped, unless both have an `article_id` and they differ (two sizes with the same receipt text are two purchases). `purchases.article_id` (text) is the article number on the receipt, in the system of the supermarket on that receipt (`receipts.store`); for AH that is the `hqId`, not the webshop id. Only the AH import sends it: a scanned photo has no article number, so the app never does. New rows get the receipt date at 12:00 Amsterdam time as `bought_at`. A receipt also takes items off the list: `match_receipt_items(p_list, p_date, p_names)` (`security definer`, because a member may not read the alias of a new receipt name yet) finds per line the best item that was added on or before the receipt date (Amsterdam days) and returns `zeker` when it is the same name or the same type through `name_type()`, otherwise it only passed the pg_trgm threshold (`0.5`). The `bon` view shows it in the same row as the purchase link (`toonKoppel()`; a line linked to a purchase of that day gets no item, `lijstItem()`): the same product is ticked by default, a look-alike only when the user ticks it (`regel.itemAan`, `vanLijst()`), and an undecided look-alike is a doubt in `bonTwijfels()`, so the stack never removes it on its own. `save_receipt` gets the `item_id` per line, checks the date again, deletes the item and inserts the purchase like `buy_item` does (item name, `item_id`, `added_by`, `item_created_at`) with the receipt data, in the same transaction; it counts them as `van_lijst`. Deleting the receipt later keeps that purchase and does not put the item back. `receipts` (`store`, `receipt_date`, `total`) only exists to recognise duplicate receipts. One photo per receipt. "Gescande bonnen" in the `aankopen` view opens the `bonnen` view (`toonBonnen()`; `aankopenOpen` stays set): the receipts of the list, each expandable to the purchases that carry its `receipt_id`, and a × that calls `delete_receipt(p_receipt)`. That RPC deletes the purchases that only came from the receipt (`item_id` is null), clears the receipt columns (including `article_id`) on purchases that were linked, and removes the receipt. `receipts` is not in the realtime publication; the view refetches when opened.

**Historic AH receipts.** Two scripts outside the app, both run by hand. `scripts/ah-bonnen` (Go, uses the `appie-go` library and the login tokens that the `ah-mcp` MCP server stores) only reads from the AH account and writes all receipts with their lines to `data/ah-bonnen.json`; `data/` is not in git. `scripts/ah-importeren.py` (Python, standard library only) logs in to Supabase with the app's email and password and stores them through the same RPCs as "Bon scannen" (`receipt_exists`, `match_receipt_lines`, `save_receipt`), so re-running adds nothing twice. Without `--echt` it is a dry run. AH only gives the abbreviated receipt text; `data/ah-namen.json` maps each text to a readable name, and lines that get the same name and the same `product_id` are merged. Discounts come per receipt and are matched to lines by name (`past()`), the ones that fit no line are dropped. The product id on a receipt is not a webshop id but AH's `hqId`, which every bonus article carries next to its webshop id; the import sends it as `article_id`. `scripts/ah-artikel-aanvullen.py` (dry run without `--echt`, reuses `ah-importeren.py`) fills `article_id` on AH purchases imported before that: it finds the receipt in `data/ah-bonnen.json` by date and total and the line by `receipt_name`, and writes through the `security definer` RPC `fill_article_ids(p_rows)`, which only touches purchases with a receipt in your lists and never overwrites an id.

**AH bonus exploration.** `scripts/ah-bonus` (Go, `appie-go` with an anonymous token, no account) writes the current bonus week to `data/ah-bonus.json`: per offer the discount text and labels, validity, and its articles with `webshop_id`, `hq_id`, title, brand, size and category; a group whose articles could not be fetched after three tries gets `mislukt`. `scripts/ah-bonus-vergelijken.py` (Python, standard library, reuses `ah-importeren.py`) lays that next to `data/ah-bonnen.json` and counts which offers hit something we buy, by id and by name. Both only read; storing the week in the database is `scripts/ah-bonus-opslaan.py` (see "Offers"). The findings are in `docs/verkenning-ah-bonus.md`.

**Service worker.** `sw.js` is network-first with a cache fallback, same-origin GET only, so Supabase and CDN requests are never cached. When adding a new static file, add it to `ASSETS`; bump the `CACHE` name to evict old caches.

## Werkwijze

Leg bij elke wijziging kort uit wat je doet en waarom, in het Nederlands.

De opbouw van de clientcode (lagen `data.js`, `logica.js`, `app.js`) en de stappen van het refactoren staan in `ARCHITECTURE.md`; houd je daar bij elke taak aan. Kern: de UI roept nooit `db.` aan, nieuwe Supabase-calls komen in `data.js`, nieuwe logica komt in `logica.js` en niet in `app.js`, en wie een onderdeel van `app.js` aanpast verhuist eerst de logica van dat onderdeel naar `logica.js` (eigen commit). Tijdens het refactoren stop je na elk domein voor een test en een commit.

Elke databasewijziging is een nieuw migratiebestand in `supabase/migrations/`, nooit meer losse SQL in het dashboard. Hoe de database er nu uitziet lees je uit die map. De commando's staan in `docs/migraties.md`.
